# Threat model

Method: STRIDE per trust boundary. Each row maps a threat to the control that addresses it and to
the test, bench script or CI job that shows the control works. `scripts/check_baseline.py`
verifies that every backticked evidence reference exists.

## System and trust boundaries

```mermaid
flowchart LR
    client[API client<br/>per-key policy] -- "TB1: network" --> api[FastAPI app<br/>auth, rate limit, body limit,<br/>closed request schema]
    api -- "TB2: tenant boundary" --> engine[Engine<br/>admission, scheduler,<br/>paged KV pool, prefix cache]
    admin[Admin key] -- "TB3: admin scope" --> adminroutes[/v1/admin/*]
    adminroutes --> engine
    adminroutes --> audit[(Hash-chained audit log)]
    disk[(Checkpoint on disk<br/>safetensors + JSON + manifest)] -- "TB4: artifacts" --> engine
    api --> obs[Logs, spans, metrics<br/>lengths and hashes only]
```

Assets: API keys; tenants' prompts and completions; one tenant's latency SLO against another
tenant's load; the integrity of the weights being served; the KV pool (memory shared by every
tenant); the admin audit trail.

Assumptions: TLS terminates in front of the service; the host, the container runtime and the
filesystem holding the checkpoint are trusted to the extent that the manifest digest is pinned out
of band; API keys map one-to-one to tenants (isolation is per key, not per end user).

## Out of scope

Network-level attacks below TLS, per-end-user isolation behind one key, fair queuing between
tenants of the same class, side channels other than the prefix cache (for example queueing delay
revealing aggregate load), and denial of service beyond a single process.
